# TZ Часть 8 — Партнёрская программа (Affiliate Program)

> **Назначение:** Техническое задание на подсистему партнёрской программы — реферальные
> ссылки для **внешних вебмастеров** (affiliates), трекинг переходов, ежедневный расчёт
> RevShare от NGR, начисление на кошелёк партнёра, кабинет партнёра и админ-панель.
>
> **Связь с существующим кодом:** `referrals` (§ MODULE_BOUNDARIES §9) — это реферальная
> программа **для самих игроков** (каждый пользователь приглашает друзей, получает 5% GGR).
> Это **другая сущность** и она НЕ переписывается. См. §2 «Разграничение».

## 1. Контекст и проблема

### 1.1. Что есть сейчас

В проекте реализована **игровая реферальная программа**:

| Что                                                  | Где                                                      |
| ---------------------------------------------------- | -------------------------------------------------------- |
| Код в `users.referral_code` (уникальный, 8 символов) | `schema.prisma:19`                                       |
| Привязка `users.referred_by` при регистрации         | `auth/application/use-cases/register.use-case.ts`        |
| Ежедневный расчёт GGR-share 5%                       | `referrals/application/referral-calc.service.ts`         |
| Cron `referral-daily`                                | `modules/maintenance/application/referrals-daily.job.ts` |
| Rate из env `REFERRAL_REWARD_RATE` (дефолт `0.05`)   | `env.validation.ts:38`                                   |

Это программа **«приведи друга-игрока»**. Она не решает задачу привлечения трафика
с внешних площадок.

### 1.2. Чего не хватает

1. **Нет отдельной сущности «партнёр».** Партнёр-вебмастер не может зарегистрироваться,
   получить трекинг-ссылку, смотреть статистику и забирать заработок.
2. **Rate зашит в env** (`REFERRAL_REWARD_RATE`) и не меняется из админки без редеплоя.
3. **Нет трекинга переходов** — нет clicks/registrations/deposits по партнёру, только
   привязка на этапе регистрации.
4. **Нет расчёта NGR.** Считается GGR (ставки − выигрыши). NGR = GGR − бонусы − комиссии
   провайдеров − эквайринг. Разница 30–50% от выплаты партнёру (см. §3.1).
5. **Нет админ-управления**: ни создания партнёра, ни изменения ставки, ни санкций.
6. **Нет антифрода** — нет защиты от самопривлечения (self-referral) и мультиаккаунтов.

### 1.3. Цель

Дать оператору инструмент получения внешнего трафика: партнёр регистрируется,
получает персональную ссылку, приводит игроков, получает RevShare с NGR игроков.
Ставка RevShare настраивается **из админ-панели** без редеплоя.

## 2. Разграничение с существующим referrals

Две подсистемы живут параллельно. Путать их нельзя.

| Критерий      | `referrals` (существует)      | `affiliate` (новая)                   |
| ------------- | ----------------------------- | ------------------------------------- |
| Кто участвует | Игрок, приглашающий игрока    | Вебмастер, приглашающий игрока        |
| Код           | `users.referral_code`         | `affiliates.tracking_code`            |
| Привязка      | `users.referred_by`           | `affiliate_attributions.affiliate_id` |
| Ставка        | 1 на всех, из env             | Индивидуальная на партнёра, из БД     |
| Расчёт        | GGR (ставки − выигрыши)       | **NGR** (GGR − бонусы − комиссии)     |
| Доступ        | Каждому игроку автоматически  | По регистрации в программе            |
| Статус        | Нет (активен автоматически)   | `pending/active/suspended/rejected`   |
| Начисление    | `ledger type=REFERRAL_REWARD` | `ledger type=CONVERSION_CREDIT`       |
| Модерация     | Нет                           | Есть (admin)                          |
| Антифрод      | Нет                           | Есть (§13)                            |
| Кабинет       | `/referral` в web             | `/affiliate` в web                    |

**Правило:** код `referrals` в рамках Части 8 **не меняется**. Общие только
`game_transactions` (источник GGR) и `ledger_entries` (приём начислений).

## 3. Исследование рынка: что важно и какие тонкости

Исследование проведено по операторским гайдам iGaming-партнёрских программ
(Track360, iREV, TrackNow, Softswiss), glossary терминов и материалам по
affiliate compliance. Ниже — выжимка того, что реально влияет на реализацию.

### 3.1. GGR ≠ NGR — главная причина споров партнёров

```
GGR = Σ ставки − Σ выигрыши
NGR = GGR − бонусы − chargebacks − комиссия провайдера − эквайринг − налоги
RevShare = NGR × ставка партнёра
```

Пример из рынка: GGR = $10 000, бонусы −$1 500, chargebacks −$300, эквайринг −$200 →
NGR = $8 000. При ставке 35% партнёр получает $2 800, а **не** $3 500.

> **Вывод для реализации:** считать и показывать партнёру **NGR с разбивкой вычетов**.
> Открытая формула = доверие партнёра. Прозрачность важнее «красивой» цифры.

### 3.2. Отрицательный перенос (negative carryover)

Когда игрок в периоде выиграл больше, чем поставил (NGR < 0), у партнёра баланс
уходит в минус и переносится на следующий период. Партнёр не получает выплату,
пока не «отыграет» долг.

Это **стандарт отрасли** и одновременно главный источник недоверия. Партнёры
торгуются за «no negative carryover» (NCNO). Оператор без переноса получает
непредсказуемый риск от игроков-выигрышников.

> **Решение для MVP (§4):** отрицательный остаток **не переносится** (NCNO-режим),
> но при NGR < 0 за период начисление не создаётся, а факт фиксируется в
> статистике. Это защищает партнёра (соответствует тренду рынка) и оставляет
> оператору рычаг: режим переноса включается флагом в админке.

### 3.3. Модели комиссий

| Модель   | Механика                              | Риск для оператора                            | Требует                         |
| -------- | ------------------------------------- | --------------------------------------------- | ------------------------------- |
| CPA      | Фикс за первую депозитную регистрацию | Трафик минимального качества, самопривлечение | Антифрод, hold 30–60 дней       |
| RevShare | % от NGR за период                    | Долгая окупаемость, споры о формуле           | Точный расчёт NGR, прозрачность |
| Hybrid   | CPA + сниженный RevShare              | Двойная сложность                             | Оба механизма сразу             |

**Бенчмарки 2026 (iGaming):** CPA $50–$400 (Tier-1 GEO до $200–$400), RevShare 25–45% NGR.
Новички обычно стартуют с 20–25%.

> **Решение:** в MVP только **RevShare** (§4). Ставка по умолчанию **20%** —
> это нижняя граница рынка для новых партнёров, даёт запас для пересмотра вверх.

### 3.4. Квалификация и hold-период

Даже в RevShare-программах CPA-логика живёт в виде **порога допуска**:

- игрок должен сделать **первый депозит** (иначе конверсии нет вообще);
- игрок должен **пройти KYC** (иначе это не реальный игрок);
- начисление попадает в статус `pending` и **доживает hold-период** (30 дней в iGaming —

> стандарт), пока не подтвердится, что игрок не сделал chargeback.

> **Решение для MVP:** квалификационные правила (минимальный депозит, требование KYC)
> задаются **настройками в админке**. Hold-период MVP = **0 дней** (начисление сразу),
> но сама инфраструктура статусов `pending → approved → paid` закладывается, чтобы
> hold можно было включить флагом без изменения схемы.

### 3.5. Атрибуция и cookie-окно

- Отраслевая норма cookie-окна: **30–90 дней**. Ниже 30 — ниже рынка.
- Last-click модель: последний клик с валидным партнёрским кодом «выигрывает».
- Ограничения cookies: Safari ITP режет срок до 7 дней, Firefox ETP — аналогично.
  Отсюда интерес к **server-to-server (S2S) postback** и first-party cookies.
- Повторные клики того же партнёра не перебивают его же атрибуцию.
- Клик по ссылке **заблокированного/ suspended** партнёра не создаёт атрибуцию.

> **Решение для MVP:** атрибуция через **first-party cookie + серверный fallback**.
> Cookie `aff_code` ставится публичным endpoint'ом, хранится в БД (`affiliate_clicks`),
> срок 30 дней (настраивается). Параллельно поддерживается передача кода в
> localStorage → при регистрации код дублируется. Это дешёвый « cookieless-lite »,
> полноценный S2S postback — вне MVP (§20).

### 3.6. Самопривлечение и мультиаккаунты (главный вектор мошенничества)

Топ-паттерны фрода в гемблинг-аффилиатах:

| Паттерн                  | Суть                                             | Защита                                                 |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------ |
| **Self-referral**        | Партнёр регистрирует игрока по своей ссылке      | Сравнение IP/UA/платёжного метода партнёра и игрока    |
| **Мультиаккаунт**        | Один человек — много аккаунтов по разным ссылкам | Device/IP-сигнатура, лимит конверсий на IP             |
| **Cookie stuffing**      | Подстановка cookie без реального перехода        | Серверная валидация Referer, серверная генерация клика |
| **Incentivized traffic** | Кэшбэк игроку из комиссии партнёра               | Ручная проверка, лимиты на FTD-конверсии               |
| **Brand bidding**        | Контекстная реклама по бренду оператора          | Правила в соглашении, мониторинг                       |
| **Демо-трафик**          | Регистрации ради объёма, без депозита            | Порог допуска, hold                                    |

> **Вывод:** даже при «открытой регистрации без модерации» (решение §4) **минимум
> автоматических проверок обязателен**, иначе программа станет инструментом
> самообмана. Реализуем 4 автоматических правила (§13.2) — они дешёвые и
> снимают основную часть риска.

### 3.7. Обязательства оператора по compliance

Оператор **отвечает за действия партнёра** (MGA/UKGC LCCP), даже если вины
в формальном смысле на партнёре нет. Отсюда обязательные элементы:

- **Регистр партнёров** — кто участвует, с какого момента, на каких условиях.
- **Письменное соглашение** с каждым партнёром (обязателен юр. документ).
- **Правила рекламы**: запрет обещаний «безрисковый выигрыш», обязательное
  упоминание 18+, запрет таргетинга на несовершеннолетних и на самоисключённых.
- **Аудит-трейл**: кто менял ставку, кто блокировал партнёра, когда.
- Ответственная игра: партнёрские креативы **не должны** привлекать
  самоисключённых игроков. В проекте есть `selfExcludedUntil` в `user_settings` —

> это готовый хук для блокировки.

### 3.8. Сроки и активация

- Окно активации нового партнёра: **7–14 дней**. Нет кликов за 2 недели →
  вероятность стать активным партнёром падает ниже 10%.
- Партнёрам нужны: ссылка, креативы, **прозрачная статистика в реальном времени**,
  предсказуемый график выплат.
- KPI программы: активация > 30%, LTV/CAC > 3:1, доля спорных начислений < 3%,
  флаг фрода 2–8%.

### 3.9. Психология: почему прозрачность — не опция

Топ-партнёры выбирают программу не только по ставке, а по **операционной
надёжности**: точность отчётов, скорость выплат, открытость правил. Ошибка
в расчёте на 1 период разрушает отношения быстрее, чем низкая ставка их привлекает.
Отсюда обязательное требование: **партнёр видит ровно те же цифры, что и админ**.

## 5. Границы подсистемы (scope)

### 5.1. Входит в MVP

- Регистрация партнёра (логин/пароль, отдельная сущность `affiliates`).
- Трекинг-ссылка + deep-link на страницу/игру.
- Endpoint клика с записью в БД, установкой cookie, редиректом.
- Привязка игрока к партнёру при регистрации.
- Ежедневный расчёт NGR и RevShare в начисления.
- Начисление на кошелёк партнёра.
- Кабинет партнёра: статистика, начисления, рефералы, ссылка.
- Admin-API: партнёры, индивидуальные ставки, начисления, сводка.
- Admin-UI: страница партнёрской программы с настройкой процентов.
- Автоматический антифрод (4 правила, §13.2).
- Самоисключение партнёра из программы.
- Аудит-лог всех admin-действий.

### 5.2. Явно НЕ входит (фаза 2+)

| Что                             | Почему не в MVP                             | Когда                  |
| ------------------------------- | ------------------------------------------- | ---------------------- |
| CPA и Hybrid комиссии           | Умножает математику и антифрод вдвое        | Фаза 2                 |
| Субаффилиаты / многоуровневость | Регуляторный риск, «пирамиды»               | Не планируется         |
| Реальные выплаты с заявками     | Отдельный финансовый контур + KYC партнёра  | Фаза 3                 |
| S2S postback                    | Требует публичного API для внешних трекеров | Фаза 2                 |
| Промо-коды / купоны             | В релизе нет бонусного движка (ТЗ ч.5 §2.8) | После бонусного движка |
| Brand bidding мониторинг        | Нет рекламного трафика для контроля         | Фаза 2                 |
| Креативы/баннеры партнёров      | Отдельная подсистема CDN                    | Фаза 2                 |
| API для внешних партнёров       | Портал покрывает MVP-сценарии               | Фаза 2                 |
| Email-уведомления партнёрам     | Не критично; в проекте есть очередь `email` | Фаза 2                 |

## 6. Модель данных

Все деньги — `Decimal(20, 8)`, в коде `string` + `decimal.js` (правило §1 `AI_DEVELOPMENT_RULES`).
Денежные поля не `number`. Ставки — `Decimal(5, 4)` (макс 99.9999%).

## 7. Трекинг и атрибуция

### 7.1. Формат ссылки

```
https://{DOMAIN}/go/{tracking_code}?p={path}&c={campaign_id}&s={sub_id}
```

| Параметр                             | Назначение                                  | Обязательный |
| ------------------------------------ | ------------------------------------------- | ------------ |
| `p`                                  | Путь лендинга (например `casino/sweetbono`) | нет          |
| `c`                                  | ID кампании партнёра (для его отчётности)   | нет          |
| `s`                                  | Sub-ID (ad id, источник внутри кампании)    | нет          |
| `utm_source/utm_medium/utm_campaign` | Стандартные UTM, дублируются в `c`/`s`      | нет          |

**Deep-link:** `p` может указывать на страницу игры → после 302 пользователь попадает
на `/casino/{slug}/play`. Если игра не найдена/выключена — fallback на `/casino`.

### 7.2. Обработка клика

```
GET /go/{code}?p=...&c=...&s=...
  1. Найти affiliate по tracking_code (SELECT, индекс)
  2. Если не найден          → 302 на /casino (без cookie) + лог warn
  3. Если status != active   → 302 на /casino (без cookie) + лог warn
  4. Если код в blocklist    → 302 на /casino (без cookie)
  5. Валидировать p (whitelist путей, защита от open redirect)
  6. Записать affiliate_clicks (ip_hash, ua, referer_host, geo)
  7. Обновить affiliates.last_click_at
  8. Ответ: 302 + Set-Cookie: aff_code={code}; Max-Age=30d; HttpOnly=false;
     SameSite=Lax; Secure; Path=/
  9. 302 на https://{DOMAIN}{p ?? '/casino'}
```

> **Почему `HttpOnly=false`:** фронтенду нужно прочитать код из cookie и положить в
> localStorage, чтобы пережить ITP-усечение в Safari/Firefox. Это идентификатор
> партнёра, не секрет — не считается утечкой.

> **Защита от open redirect:** `p` проходит whitelist регулярных выражений —
> только пути внутри каталога `/casino/...`. Абсолютные URL, `//evil.com`, `\`,
> `%00` отбрасываются с fallback на `/casino`.

> **Почему запись в БД синхронная:** клик — это точка невозврата для аналитики.
> Если не записать сейчас, в аналитике партнёра будут дыры. Запись идёт
> fire-and-forget с `void` на ошибку (fail-open к редиректу: редирект пользователя
> важнее аналитики), ошибка логируется.

### 7.3. Привязка при регистрации

Порядок приоритета источника кода:

1. Query-параметр `ref` в URL регистрации (явная передача).
2. `localStorage.aff_code` (фронтенд перехватывает при монтировании).
3. Cookie `aff_code`.

Приоритет объясняется просто: cookie может пережить явный `?ref=` от **другого**
партнёра, но явный параметр — более сильный сигнал намерения.

**Алгоритм `AttributePlayerUseCase.execute`:**

```
1. Извлечь код (ref → localStorage → cookie)
2. affiliate = findByTrackingCode(code)
3. Нет кода / affiliate / status != active → сохранить user без атрибуции, выйти
4. EXISTS affiliate_attributions WHERE player_id = user.id?
   → ДА: другая атрибуция уже была — НЕ переприсваивать, выйти
   (защита от «перехвата» игрока конкурирующим партнёром)
5. Антифрод-чеки (§13.2): self-referral, дубли по IP/UA
   → совпадение: создать атрибуцию со status=rejected + причину, комиссий не будет
6. Создать affiliate_attributions (status=pending, click_id из cookie-контекста)
7. Вернуть affiliate_id для использования в бонусной логике (если появится)
```

> **Вызов из auth:** `register.use-case.ts` и `oauth-user-provisioning.service`.
> Вызывается **через `AffiliateFacade`** (не через прямой импорт репозитория) —
> правило §4 `AI_DEVELOPMENT_RULES`.

### 7.4. Квалификация (qualification)

Атрибуция `pending` становится `qualified` при выполнении **всех** условий:

| Условие        | Проверка                                                                | Настройка               |
| -------------- | ----------------------------------------------------------------------- | ----------------------- |
| Сделан депозит | `payment_requests` со статусом `completed`, `player_id`, `type=DEPOSIT` | обязательно             |
| Сумма ≥ порога | `amount >= affiliate_min_deposit`                                       | настройка               |
| Пройден KYC    | `kyc_profiles.status = approved`                                        | `affiliate_require_kyc` |

Квалификация проверяется **синхронно в момент завершения депозита**
(событие в payments-модуле) и **дополнительно подтверждается** в начале
суточного расчёта — на случай, если KYC завершился позже депозита.

## 8. Бизнес-логика: расчёт RevShare

### 8.1. Формула

```
Для каждого (partner, player, currency) за период:
  bet_sum        = Σ game_transactions.amount   WHERE type='bet'  AND player AND период
  win_sum        = Σ game_transactions.amount   WHERE type='win'  AND player AND период
  rollback_sum   = Σ game_transactions.amount   WHERE type='rollback' AND player AND период

  ggr_amount     = bet_sum − win_sum − rollback_sum
  bonus_sum      = Σ ledger_entries.amount      WHERE type='BONUS' AND player AND период
  provider_fee   = Σ комиссий провайдеров (см. §8.3)
  ngr_amount     = ggr_amount − bonus_sum − provider_fee_sum

  commission     = ngr_amount > 0 ? ngr_amount × affiliate.revshare_rate : 0
```

### 8.2. Отрицательный NGR

| `ngr_amount` | `affiliate_negative_carryover` | Поведение                                                                                                   |
| ------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `> 0`        | любое                          | Создать начисление, начислить                                                                               |
| `<= 0`       | `false` (MVP)                  | **Начисление не создаётся.** Запись в статистику: `ngr<=0`                                                  |
| `<= 0`       | `true`                         | Создать начисление `status=cancelled`, `commission_amount=0`, накопить долг в `affiliates.negative_balance` |

> **Важно:** при `ngr <= 0` и `carryover=false` начисление **не создаётся вообще** —
> это сохраняет уникальный индекс чистым и не плодит нулевые строки.

### 8.3. Комиссия game-провайдера

В текущей схеме у `game_providers` есть `config` (jsonb), но **фактические
комиссии не вычисляются и нигде не пишутся**. Это осознанное упрощение MVP
(см. ТЗ ч.4, `PROVIDER_INTEGRATION_STRATEGY.md`).

> **Решение MVP:** `provider_fee_sum = 0` всегда. Поле в таблице заведено сразу,
> чтобы при появлении реальных данных (фаза 2) не менять схему.
> **Явно зафиксировано в `partner-calculator.ts` как `providerFee = ZERO`** с
> комментарием и TODO — не молчаливое упрощение.

### 8.4. Периодизация

- Период — **календарные сутки UTC** (совпадает с существующим `referral-daily`).
- `period_start` — `date`, не `timestamptz` (как в `referral_rewards`).
- Расчёт за вчера. Повторный запуск за тот же период — идемпотентен
  (уникальный индекс + проверка существования).

### 8.5. Начисление на кошелёк

```typescript
// idempotencyKey — детерминированный, дедуп на уровне ledger_entries
const idempotencyKey = `aff_${commission.id}`
```

| Колонка         | Значение                                                          |
| --------------- | ----------------------------------------------------------------- |
| `type`          | `CONVERSION_CREDIT` (существующий enum `LedgerEntryType`)         |
| `user_id`       | `affiliate.user_id` — **партнёр = пользователь**                  |
| `currency`      | Валюта расчёта                                                    |
| `amount`        | `commission_amount`                                               |
| `referenceType` | `AffiliateCommission`                                             |
| `referenceId`   | `commission.id`                                                   |
| `description`   | `Affiliate commission {period} (player {id})`                     |
| `metadata`      | `{ affiliateId, playerId, periodStart, ngrAmount, revshareRate }` |

**Критично:** `affiliates` связана с `users` через `user_id` (FK, unique) —
партнёр получает реальный кошелёк игрока, поэтому `WalletFacade.credit()`
работает без изменений, а вывод идёт через существующую кассу (решение D3).

> ⚠️ Партнёр **обязан** иметь KYC-одобренный аккаунт для реального вывода,
> иначе лимит 5000 RUB (ТЗ ч.2). Это документируется в соглашении партнёра.

### 8.6. Порядок операций (транзакционность)

```
1. Проверить уникальным индексом: начисление за (aff, player, period, ccy) есть?
   → есть: пропустить (идемпотентность)
2. Создать affiliate_commissions (status=pending)   ← точка идемпотентности
3. ВНЕ транзакции: WalletFacade.credit({ idempotencyKey: `aff_${id}` })
4. Успех → status=approved, credited_at=now, ledger_entry_id
   Ошибка  → status остаётся pending, commission_amount НЕ обнулять,
             повторная попытка на следующем запуске
```

> **Почему кредит вне транзакции:** `WalletFacade.credit` сам открывает
> транзакцию с optimistic locking. Вложенная транзакция + retry-цикл внутри
> нашей транзакции → deadlock-риск и долгий transaction. Правило §7.3
> `AI_DEVELOPMENT_RULES` (non-blocking mutations) требует быстрых транзакций.
> Шаг 2 **до** кредита гарантирует, что повторный запуск не создаст дубль.

```
/dashboard/affiliate/attributions       — атрибуции, ручная квалификация/отказ
/dashboard/affiliate/settings           — настройки программы (superadmin)
```

### 11.2. Управление процентом — ключевое требование

Три уровня задания ставки (приоритет сверху вниз):

| Уровень                   | Где                               | Кто меняет               | Приоритет     |
| ------------------------- | --------------------------------- | ------------------------ | ------------- |
| **Индивидуальная ставка** | `affiliates.revshare_rate`        | admin, карточка партнёра | 1 (побеждает) |
| Ставка по умолчанию       | `affiliate_default_revshare_rate` | superadmin, настройки    | 2             |
| Fallback                  | `REFERRAL_REWARD_RATE` / `0.05`   | env                      | 3             |

**Поведение при изменении индивидуальной ставки:**

> Ставка **не применяется задним числом**. Уже рассчитанные начисления хранят
> снимок `revshare_rate` на момент расчёта. Новая ставка действует со следующего
> периода. Это обязательно — иначе пересчёт задним числом приводит к
> необходимости отзыва выплаченных средств.

Изменение ставки → обязательный `audit_logs`:
`action: 'affiliate.rate.changed'`, `payload: { from, to, affiliateId, adminId }`.

### 11.3. Санкции

| Действие        | Эффект                                                                                                         | Роль       |
| --------------- | -------------------------------------------------------------------------------------------------------------- | ---------- |
| `suspended`     | Клики не атрибутируются, новые регистрации не привязываются. **Существующие начисления и история сохраняются** | admin      |
| `rejected`      | Полный отказ от работы. Поле `suspended_reason` обязательно                                                    | superadmin |
| `rate override` | Индивидуальная ставка вместо дефолтной                                                                         | admin      |
| `code reset`    | Ротация `tracking_code`, старая ссылка перестаёт работать                                                      | admin      |
| `manual credit` | Разовая выплата через `WalletFacade.credit` (`ADMIN_CREDIT`)                                                   | superadmin |

> **Асимметрия при suspend:** начисления за прошлые периоды **не отменяются**.
> Отмена — только явным действием (см. §11.4). Так партнёр не теряет
> заработанное за уже закрытые периоды.

### 11.4. Clawback (отмена начислений)

Полноценный clawback в MVP **не реализуется** (нет выплат — нечего возвращать).
Закладывается только модель:

- Начисление в `approved` можно перевести в `cancelled` **только superadmin'ом**.
- Обязателен `reject_reason` из справочника:
  `self_referral | fraud | chargeback | kyc_fail | dormancy | manual`.
- Если начисление уже начислено на кошелёк — отмена выполняется
  `WalletFacade.debit` с компенсирующим `idempotencyKey`
  (`aff_clawback_{commissionId}`), **отдельной операцией** после коммита отмены.
- Полный перечень триггеров и лимиты — фаза 2 (когда появятся реальные выплаты).

## 13. Антифрод

### 13.1. Почему это не опция

Гемблинг-вертикаль — цель №1 для фрода: **стоимость одного фрод-конверсии равна
стоимости настоящей конверсии**, а реальной ценности ноль. При открытой
регистрации без модерации (решение D4) автоматические проверки — единственный
барьер. Исследования оценивают потери iGaming-операторов от affiliate-фрода
в сотни миллионов долларов в год.

### 13.2. Автоматические правила (MVP)

| #   | Правило                              | Логика                                                                               | Действие                                                             |
| --- | ------------------------------------ | ------------------------------------------------------------------------------------ | -------------------------------------------------------------------- |
| F1  | **Self-referral по IP**              | Хеш IP последнего клика партнёра == хеш IP регистрации игрока                        | `status=rejected`, `is_self_referral=true`, reason `self_referral`   |
| F2  | **Self-referral по User-Agent**      | UA последнего клика партнёра == UA регистрации (точное совпадение)                   | То же                                                                |
| F3  | **Дубли по устройству/IP-сигнатуре** | > 3 квалифицированных игроков с одного IP за 24 ч на одного партнёра                 | Авто-подвес партнёра, reason `ip_flood`                              |
| F4  | **Депозит ровно на порог**           | `amount` в пределах 1% от `affiliate_min_deposit` (классический признак «минималки») | Пометить атрибуцию `needs_review` в `reject_reason` (не блокировать) |

**Дополнительные правила уровня расчёта (без блокировки):**

| #   | Правило                      | Действие                                         |
| --- | ---------------------------- | ------------------------------------------------ |
| F5  | NGR ≤ 0 в периоде            | Начисление не создаётся (§8.2)                   |
| F6  | Игрок без депозита > 30 дней | Исключается из активных, комиссия не начисляется |

> **Ограничение применимости:** F1/F2 сравнивают партнёра и игрока **по одному
> устройству**. Ложные срабатывания возможны (офис, мобильный оператор, CGNAT).
> Поэтому F1/F2 дают **`rejected` с явной причиной и возможностью ручного
> перевода в `qualified` админом**, а не удаление записи. Это сознательный
> компромисс «безопасность vs. ложные блокировки».

### 13.3. Ручная работа

- Список атрибуций с фильтром по `reject_reason` / `status`.
- Ручная квалификация (`POST .../qualify`) и ручной отказ (`POST .../reject`).
- Все ручные действия → `audit_logs`.
- Админ-UI показывает партнёру **причину отказа** (код) — партнёр может оспорить.

### 13.4. Что осознанно не делаем в MVP

Device fingerprinting, поведенческий ML, графы связей между аккаунтами,
корпоративные e-mail-домены. Требуют инфраструктуры и не дают эффекта
на масштабе < 50 партнёров. Зафиксировано как фаза 2.

Новая очередь не нужна — используется существующая `maintenance`

| Job                        | Интервал      | Что делает                                    | Идемпотентность              |
| -------------------------- | ------------- | --------------------------------------------- | ---------------------------- |

| `affiliate-clicks-cleanup` | 24 ч          | `deleteMany` кликов старше retention          | Условный delete              |
| `affiliate-qualification`  | 1 ч           | Проверка квалификации `pending` → `qualified` | Условный update              |

**Регистрация:** добавить имена в `MAINTENANCE_JOBS` (`queue.types.ts:4-10`),
классы — в `modules/maintenance/application/*.job.ts`, интервалы — из
`JOB_AFFILIATE_*_EVERY_MS` в `env.validation.ts` (по образцу `JOB_REFERRAL_DAILY_EVERY_MS`).

**Идемпотентность `affiliate-daily`:**

```
1. dateStr = вчера (UTC) либо из payload ручного триггера
2. Для каждой qualified-атрибуции с first_deposit_at ≤ конец периода:
     for currency in currencies(player, period):
       a. Уже есть начисление? → skip
       b. Суммы (UC-AFF-08)
       c. NGR, комиссия (UC-AFF-09)
       d. Начисление (UC-AFF-10)
3. Вернуть { processed, credited, period }
```

> Повторный запуск (ручной триггер после автоматического) **не создаст дублей**
> — это гарантирует `@@unique([affiliate_id, player_id, period_start, currency])`.

**Расчёт по валютам:** как в существующем `referral-calc.service.ts` — для каждой
валюты, в которой играл игрок, отдельное начисление. Суммы в разных валютах
**не смешиваются**.

## 16. Безопасность

| Требование              | Реализация                                                                              |
| ----------------------- | --------------------------------------------------------------------------------------- |
| Пароли партнёров        | argon2id (как у игроков)                                                                |
| JWT партнёра            | Отдельный `aud: 'affiliate'`, отдельные cookie/сессии, **не** пересекается с user/admin |
| Выход партнёра          | `GET /go/:code` — **публичный без auth**, обязателен `Throttle`                         |
| Rate-limit регистрации  | 5/hour на IP                                                                            |
| Rate-limit логина       | 10/hour на IP, блокировка при 5 неудачах                                                |
| Логи                    | Никогда не логировать пароль/токен. IP — только хеш                                     |
| IP в БД                 | Только SHA-256 с солью (`INTERNAL_API_SECRET`). Сырой IP не сохраняется                 |
| Open redirect           | Whitelist путей в `p` (§7.2)                                                            |
| Rate injection          | Ставка из админки валидируется Zod: `0 ≤ rate ≤ 1`, `Decimal`                           |
| Деньги                  | Только `string` + `decimal.js`. Ставка — `Decimal`, не `number`                         |
| Идемпотентность кредита | `aff_{commission.id}` + проверка дубликата в ledger                                     |
| Admin-действия          | Всё через `AuditLogService` (`admin` actor)                                             |
| SQL injection           | Только Prisma параметризованные запросы, никаких `$queryRaw` с конкатенацией            |

**JWT-аудитория партнёра:** добавить `AFFILIATE_JWT_SECRET` и
`AFFILIATE_JWT_*_EXPIRES_IN` либо переиспользовать user-секрет с `aud`.
**Решение MVP:** отдельный секрет `AFFILIATE_JWT_SECRET` (минимум 64 символа) —
явное разделение контуров, проверяется `env.validation.ts` и `isUnsafeSecret`.

## 19. Критерии приёмки

| #   | Сценарий                                             | Ожидаемый результат                                                                  |
| --- | ---------------------------------------------------- | ------------------------------------------------------------------------------------ |
| A1  | Регистрация партнёра                                 | Создан `affiliate`, выдан `tracking_code`, работает вход                             |
| A2  | Клик по ссылке партнёра                              | Запись в `affiliate_clicks`, cookie `aff_code` установлена, 302 на лендинг           |
| A3  | Клик по коду несуществующего партнёра                | 302 на `/casino`, cookie **не** установлена, лог `warn`                              |
| A4  | Клик по ссылке `suspended` партнёра                  | 302 на `/casino`, без cookie                                                         |
| A5  | Deep-link `?p=casino/sweetbono`                      | 302 на страницу игры                                                                 |
| A6  | Deep-link `?p=https://evil.com`                      | **Отброшен**, fallback на `/casino` (нет open redirect)                              |
| A7  | Игрок регистрируется с `?ref=CODE`                   | Создана атрибуция `pending`                                                          |
| A8  | Игрок уже привязан к партнёру A, приходит с кодом B  | Привязка **не меняется**, ошибка `AFFILIATE_ALREADY_ATTRIBUTED`                      |
| A9  | Игрок делает депозит ≥ порога + KYC                  | Атрибуция → `qualified`                                                              |
| A10 | Игрок делает депозит < порога                        | Остаётся `pending`, начислений нет                                                   |
| A11 | Партнёр и игрок с одного IP                          | Атрибуция `rejected`, `is_self_referral=true`, reason `self_referral`                |
| A12 | Админ меняет ставку 20% → 30%                        | Новая ставка применяется со **следующего** периода; прошлые начисления сохраняют 20% |
| A13 | Сумма NGR = 1000, ставка 20%                         | `commission_amount = 200.00`                                                         |
| A14 | NGR отрицательный, carryover выкл                    | Начисление **не создаётся**                                                          |
| A15 | Запуск `affiliate-daily` дважды за день              | Начислений не удвоено (уникальный индекс)                                            |
| A16 | Два конкурентных запуска `affiliate-daily`           | Один успевает, второй получает `P2002` и пропускает                                  |
| A17 | Начисление кредитуется на кошелёк партнёра           | `ledger_entries` с `type=CONVERSION_CREDIT`, `idempotencyKey=aff_{id}`               |
| A18 | Кредит упал (ошибка wallet)                          | Начисление остаётся `pending`, повторная попытка на след. запуске                    |
| A19 | Двойной клик по кнопке «вывести»                     | Одна запись начисления (идемпотентность)                                             |
| A20 | Партнёр открывает чужой `affiliate_id` в query       | Игнорируется, используется ID из JWT                                                 |
| A21 | Клик по ссылке при `AFFILIATE_ENABLED=false`         | 302 на `/casino`, без cookie                                                         |
| A22 | Сумма NGR = 1000, ставка из `system_settings` = 0.25 | `commission_amount = 250.00`                                                         |
| A23 | Партнёр сам меняет свою ставку                       | **403** — только admin                                                               |
| A24 | Вход партнёра в игровой кабинет                      | Partner-JWT **не принимается** user-контроллерами (разные `aud`)                     |
| A25 | Cleanup кликов                                       | Клики старше retention удалены, свежие сохранены                                     |

> **Главный принцип:** партнёрская программа — это **обещание денег**. Ошибка
> в расчёте на один период разрушает доверие быстрее, чем низкая ставка
> его не создаёт. Поэтому приоритеты: (1) прозрачность расчёта, (2) идемпотентность,
> (3) воспроизводимость цифр у партнёра и у админа, (4) — только потом автоматизация.
