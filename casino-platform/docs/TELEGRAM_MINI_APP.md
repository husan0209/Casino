# Telegram Mini App — вход по initData и жизнь внутри клиента

Живой документ. Расхождение с кодом — дефект документа; сверять по
[IMPLEMENTATION_GAPS.md](./IMPLEMENTATION_GAPS.md) (GAP-04 — вход через Telegram,
GAP-42 — верификация подписей OAuth, GAP-75 — Mini App).

## 1. Что это

Mini App — это НЕ второе приложение. Это тот же `apps/web`, который игрок
открывает из чата с ботом: Telegram показывает наш сайт в своём окне, и игрок
уже опознан — без телефона, без пароля, без экрана входа.

Вокруг Telegram в проекте два разных входа, и их нельзя путать:

| Вход              | Как выглядит у игрока                                    | Подпись проверяется по  | Секрет подписи                                          | Код                                                                                       |
| ----------------- | -------------------------------------------------------- | ----------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Login Widget      | редирект на oauth.telegram.org, экран «Продолжить как …» | hash от объекта виджета | SHA256 от TELEGRAM_BOT_TOKEN                            | `apps/api/src/modules/auth/application/use-cases/oauth/telegram-login.use-case.ts`        |
| Mini App (GAP-75) | приложение открыто из бота, входа не видно               | hash от init_data       | HMAC-SHA256 с ключом «WebAppData» на TELEGRAM_BOT_TOKEN | `apps/api/src/modules/auth/application/use-cases/oauth/telegram-webapp-login.use-case.ts` |

Оба входа ведут в один аккаунт: связка живёт в `auth_providers`
(`provider=telegram`, `provider_user_id` = числовой id Telegram), поэтому
игрок, вошедший по кнопке и по кнопке из Mini App — один и тот же пользователь.
Новых таблиц, провайдеров и env-переменных для Mini App не потребовалось.

## 2. Как это работает

1. Игрок открывает приложение из бота. Клиент добавляет к адресу параметры
   инициализации (во фрагменте URL — их читает официальный SDK) и подписанный
   набор данных `initData`.
2. `apps/web` определяет, что его открыл КЛИЕНТ Telegram, и берёт `initData`
   РОВНО так, как её отдал клиент: `init_data` уходит на API одной строкой, без
   разбора и без пересборки (`apps/web/src/lib/telegram-webapp-auth.ts`).
3. API проверяет подпись на сервере и только потом идёт в базу
   (`POST /auth/telegram/webapp`, ответ — те же accessToken + refresh-cookie,
   что у любого OAuth-входа).
4. Дальше работает обычный сайт: кошелёк, касса, игры. Реквизиты входа
   выметаются из адреса при любом исходе — `initData` сама по себе является
   токеном входа.

Три правила, которые нельзя терять при правках:

- **Ссылка не логинит.** `init_data` — предъявительский токен: подпись доказывает
  «это выдал Telegram», но не доказывает «этот браузер запустили из бота».
  Поэтому Mini App-режим включается только по сигналам, которые подделывает сам
  клиент (UA WebView, объект `window.Telegram`, влитый до нашей гидрации, или
  нахождение во фрейме — а `frame-ancestors` допускает сюда только telegram.org),
  и никогда — по параметрам `tgWebApp*` в адресе. Ссылка с чужой подписью,
  открытая в обычном браузере, не должна ни логинить, ни тянуть сторонний скрипт;
  кейс закреплён в `apps/web/test/telegram-webapp.spec.tsx`.
- **Регистрация не молчаливая.** Mini App входит в уже существующий аккаунт.
  Новый игрок получает отказ и проходит через экран подтверждения виджета, где
  видно, под каким именем он заходит: заводить беспарольный кошелёк по ссылке —
  значит дать атакующему втягивать жертв в СВОЙ профиль.
- **Секреты разные.** Сводить виджет и Mini App в общий код проверки нельзя:
  способ вывода секрета отличается — это разные протоколы одного и того же
  токена. Регрессию держат
  `apps/api/test/telegram-webapp-verify.spec.ts` и
  `apps/api/test/oauth-verify.spec.ts` по отдельности.
- **Значения раскодируются один раз.** Внутри `init_data` поле `user` — это
  JSON-строка, а не объект. Если её распарсить и сериализовать обратно,
  порядок ключей и экранирование поплывут, и подпись разойдётся только на
  живом устройстве — в тестах с ASCII-именами такой дефект не виден. Кейс с
  кириллицей, `+`, `&` и `%` в имени закреплён в спеке.

## 3. Настройка — шаги владельца в BotFather

Делает владелец, один раз, в своём аккаунте Telegram. Агент эти шаги не выполняет.

1. Бот уже существует, `TELEGRAM_BOT_TOKEN` лежит на API (см.
   [ENVIRONMENT_VARIABLES.md](./ENVIRONMENT_VARIABLES.md) §7).
2. В @BotFather: Commands → /newapp (или Bot Settings → Menu Button) → выбрать
   бота → указать Web App URL. Для стенда это адрес публичного хоста с
   реферальным кодом в глубокой ссылке:
   `https://<DOMAIN>/?tgWebAppStartParam=<код>` — параметр глубокой ссылки
   приходит на сервер как `referral_code` и попадает в обычную цепочку
   приглашения.
3. /domain — домен должен быть добавлен боту: без него не работает и редиректный
   вход через oauth.telegram.org (проверено на стенде в цикле GAP-04).
4. Verify Domain — опциональный шаг: он нужен только если понадобится
   `WebApp.openLink` (переход по внешней ссылке из Mini App). Сейчас мы этот
   метод не вызываем: игра либо открывается в этом же окне, либо уходит
   обычным переходом, поэтому и верификацию домена требованием не считаем.
5. Кнопка меню: Bot Settings → Menu Button → включить, «Expand» — чтобы
   приложение открывалось во всё окно. Разворот окна мы дополнительно запрашиваем
   сами через `expand()` (`apps/web/src/hooks/useTelegramSurface.ts`).

После изменения домена или заголовков прод-контур пересобирается выкаткой
([DEPLOY.md](./DEPLOY.md)); CSP отдаёт Next, поэтому правка `frame-ancestors`
требует пересборки web-образа, а не перезапуска nginx.

## 4. Что проверено и что нет

Проверено локально (машинно):

- подпись `initData`: валид, подделка, просрочка, auth_date из будущего, чужой
  токен, hash другой длины, лишнее поле в payload, `signature` вне check-строки,
  битый JSON при верной подписи, нормализация `user.id` (ведущий ноль не
  заводит второго игрока), отказ молчаливой регистрации — и что проверка опережает
  обращение к БД (`apps/api/test/telegram-webapp-verify.spec.ts`, 15 кейсов);
- связывание HTTP-слоя нового роута: форма тела, лимит длины, отказ лишним
  ключам, refresh в httpOnly-cookie с правильным path (`apps/api/test/auth-telegram-webapp-http.spec.ts`, 6 кейсов);
- клиент: silent-вход только по сигналам клиента (UA / влитый объект / фрейм),
  отказ включаться от параметров в адресе, один handshake на документ, приоритет
  `?ref=` над `start_param`, очистка адреса при любом исходе, ни одного
  стороннего скрипта в обычном браузере, повторная попытка без второго скрипта
  (`apps/web/test/telegram-webapp.spec.tsx`, 13 кейсов; спека переживает
  `--sequence.shuffle`, то есть не зависит от порядка);
- CSP: frame-ancestors с хостами Telegram и без произвольного `https:`,
  неприкосновенность `script-src` для статической сборки (регресс d201c1e) —
  `apps/web/test/csp.spec.ts`;
- nginx: проверка наследования security-заголовков проходит после снятия
  X-Frame-Options на веб-хосте;
- игровой фрейм: полный список `allow`, заглушка вместо вечной «Загрузки игры…»,
  сброс при смене игры, выход без новой вкладки
  (`apps/web/test/game-frame.spec.tsx`);
- переход демо-игры в этот же документ внутри Telegram
  (`apps/web/test/open-game-webview.spec.ts`);
- `init_data` вырезается из логов тем же списком redact, что и пароли
  (`apps/api/src/common/logger/logger.options.ts`, он же питает скраббинг Sentry).

НЕ проверено (поэтому статус в реестре — CODE_DONE, а не CLOSED):

- **живой клиент Telegram**: настоящая `initData` (наши тесты подписывают
  синтетические данные тем же алгоритмом — это самопроверка, а не эталон),
  реальный разворот окна, цвета шапки, поведение safe-area на iOS с «чёлкой»,
  клавиатура;
- **safe-area отступы**: значения `env(safe-area-inset-*)` в CSS и
  `viewport-fit=cover` машинно не проверяются — только глазами в браузере и в
  клиенте;
- **iframe провайдера внутри WebView** — главный неизвестный всей фичи: пустит
  ли провайдер встраивание в окно Telegram. Решается только на реальном
  устройстве;
- политика Telegram в отношении мини-приложений с реальными деньгами: актуальные
  Bot Terms и правила Mini App проверяет владелец (см. §6).

## 5. Остатки, о которых известно

- **Окно повтора.** Для Mini App подпись живёт 15 минут (`MAX_AUTH_AGE_SEC` в
  `telegram-webapp-login.use-case.ts`), а не сутки как у виджета: вход здесь
  молчаливый, и время жизни — та величина, которой мы платим за отсутствие
  экрана подтверждения. Одноразовость подписи (Redis-кэш использованных hash) не
  сделана; без живого клиента и статистики запусков решать это рано.
- **Лимит на входе.** Throttler считает отдельно на хендлер, поэтому у
  `/auth/telegram/webapp` свой бюджет 10 запросов/минуту на IP
  (`@Throttle` в `auth.controller.ts`), а не общий с логином. На холодный старт
  хватает; при плотном трафике из-за NAT-а игрок может упереться в лимит, и
  клиент проглотит это молча (отказ = обычный экран входа). Точечное
  переопределение лимита есть в том же контроллере как образец.
- **Кука после выхода.** `setAccessToken` пишет заголовок в axios-инстанс, а
  `logout` чистит только стор; перехватчик подменяет его при наличии токена.
  Проверялось на существующем поведении (тот же путь у OAuth-входа), отдельной
  спеки нет.
- **Партнёрский код через Mini App** идёт как `referral_code` (игровая
  рефералка). Код партнёра (`affiliate`) по OAuth-пути не прокидывается —
  `ProviderSignInInput` его не имеет, это общий остаток всех OAuth-входов, не
  только Telegram.

## 6. Риски площадки

Mini App живёт на условиях Telegram: бота могут ограничить или заблокировать, и
тогда канал исчезает целиком. Поэтому Mini App сделан **дополнительным** входом:
обычные способы (e-mail, Google, кнопка Telegram на сайте) продолжают работать, и
блокировка бота не отрезает игрока от сайта. Правила Telegram по приложениям с
реальными ставками и по рынку игрока владелец читает сам — документ это не
решает за него.
