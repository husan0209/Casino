## Анализ Optimistic Lock

- `status=11` (DUPLICATE_TRANSACTION) не встретился ни разу — дедуп не задействован
  (ставки уникальны), а исчерпание попыток выглядит как status=1 (INTERNAL_ERROR).
- Первый всплеск ошибок — уже на 10 VU (серия burst-проб до прогона: 28 из 30
  параллельных bets падали P2034 ещё до фиксов; после фиксов на 100 VU — 69%).
- Причина: `PrismaWalletTransactionRunner` открывает ОДНУ Serializable-транзакцию
  на весь bet-флоу; конкурентные Serializable-транзакции по одному кошельку
  конфликтуют на commit (Postgres 40001 → Prisma P2034). Ретрай 3× с бэкоффом
  50·n² без джиттера даёт «волны» повторных попыток и не спасает при 100 VU.
- До фиксов ошибка была хуже: P2034 вообще не ретраился (withRetry ловил только
  app-level OptimisticLockError), а текст Prisma-инвокации с локальными путями
  машины утекал провайдеру в HTTP-ответе.

## Вывод

❌ **3 retry-попыток недостаточно для профиля «много ставок/сек на одного игрока».**
Деньги целы (главный результат прогона), но 69% ставок при 100 VU получают отказ
вместо списания — для казино это прямая потеря GGR. Нужен механизм сериализации
мутаций одного кошелька — решение за владельцем (GAP-57), варианты:

- [ ] **Рекомендация:** advisory-лок `pg_advisory_xact_lock(hashtextextended(wallet_id))`
      внутри транзакции + ReadCommitted для кошелька (очередь строк вместо abort-волн);
- [ ] ИЛИ per-wallet очередь BullMQ (1 job на wallet-account);
- [ ] ИЛИ in-process per-wallet mutex (быстро, но только пока API — один инстанс).
