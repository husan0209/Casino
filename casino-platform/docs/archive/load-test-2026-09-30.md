## Что изменилось в коде (механизм)

`runInTransaction` открывал **Serializable**-транзакцию на весь bet/win/rollback-флоу.
При профиле «много ставок в секунду на одного игрока» все транзакции читали и писали
одну строку `wallet_accounts`, SSI Postgres откатывал их на коммите (SQLSTATE 40001 →
Prisma **P2034**), а 3 ретрая без джиттера давали «волны» повторов.

Вместо abort-повтора — явная очередь (`apps/api/src/modules/wallet/infrastructure/ledger/wallet-transaction-lock.ts`):

1. `pg_advisory_xact_lock(hashtextextended('casino.wallet:<userId>:<currency>', 0))`,
   взятая **первой** операцией транзакции, до чтения кошелька;
2. isolation `ReadCommitted` (advisory-лок уже сериализует кошелёк — SSI только мешал);
3. `lock_timeout` (env `WALLET_LOCK_TIMEOUT_MS`, дефолт 5с) — всплеск на одном кошельке
   не выедает пул соединений и не блокирует API для других игроков;
4. повтор (5 попыток, backoff с джиттером) на P2034 / 55P03 / `OptimisticLockError`.

Проверка `version` в ledger сохранена как второй рубеж, все деньги по-прежнему
идут строкой + `decimal.js` в `DECIMAL(20,8)`.

Читать так: **сама транзакция занимает ~20 мс** (1 VU, без ожидания). С ростом
конкуренции одного кошелька латентность растёт **линейно** — это ожидание в очереди
advisory-лока, а не отказ. Потолок одного кошелька — ~85-90 ставок/с: он
последователен по построению. Провал старого порога `p(95)<500` при 100 VU означал
не дефект, а требование параллелизма от последовательного ресурса.

## Доказательство, что лок — пер-кошелёк (а не глобальный)

10 разных игроков, 20 VU, одновременно:

| Метрика | Значение |
|---------|----------|
| `checks_succeeded` | 100.00% (15 620 / 15 620) |
| `http_req_failed` | 0.00% |
| `http_reqs` | 7 810 → **165 rps** |
| `http_req_duration` p95 | **169 ms** |
| Целостность | по всем 10 кошелькам `version − 1 == число ставок`, баланс сходится |

165 rps против ~82 rps на одном кошельке: разные кошельки не блокируют друг друга,
система масштабируется по игрокам. Это и есть смысл ключа `userId+currency`.

## Находка про метрики (важно для следующих прогонов)

Старый порог `http_req_failed: rate<0.01` был **слеп** к исходному дефекту: провайдеру
нельзя отвечать 5xx (он зациклит ретраи), поэтому отказы приходили как HTTP 200 +
`{status: 1}` и k6 показывал `0.00% failed` при 69.4% отказов. Ловит их только
проверка тела ответа. Поэтому главный гейт перенесён на `checks: ['rate>0.99']`,
а `http_req_duration` опущен до санитарного `p(95)<2000` (потолок «не зависло»).

## Действия

- [x] Реализован advisory-лок + ReadCommitted + `lock_timeout` + повтор с джиттером.
- [x] Контракт `runInTransaction` теперь требует кошелёк (`WalletLockTarget`) — нельзя
      забыть сериализацию; `bet`/`win`/`rollback` в casino передают кошелёк игрока.
- [x] Оба «денежных» пути (solo credit/debit и lock/unlock/confirm) идут через одну
      примитиву, поведение одинаково.
- [x] Ловушка, найденная интеграционным тестом: `pg_advisory_xact_lock` возвращает
      `void`, который Prisma не десериализует в `$queryRaw` — приведён к `::text`.
- [x] Новый интеграционный тест на реальном Postgres: 20 параллельных списаний
      одного кошелька — все проходят, баланс и `version` сходятся.
- [x] Прогон 10/50/100 VU и многокошелёчный прогон — успех 100%, деньги целы.
- [x] Трекер `GAP-57` закрыт с ADR; пороги k6 исправлены на ловящие реальный дефект.
